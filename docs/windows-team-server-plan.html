Private OctiqFlow state

Each member gets a separate profile, chat transcript store, terminal process set, settings, and workspace registry.

⌘

Private source work

The same repository is cloned separately for each member. Uncommitted files, indexes, stashes, and build output never overlap.

Shared AI provider

Claude and Codex use the accepted shared account. OctiqFlow does not promise provider-credential isolation between trusted members.

Why this fits the current product: OctiqFlow currently keeps its profile, service state, and event bus at process scope. One process per member turns that existing boundary into a clean user boundary without first refactoring the entire backend for multi-tenancy.
Windows environment

Use Windows Server 2022 for the 4.8 baseline

Windows Server 2022 includes .NET Framework 4.8. The runtime alone is not enough for builds; the server also needs the matching Developer Pack, Targeting Pack, and build toolchain.

Base operating system

  • Windows Server 2022, fully patched
  • Fast SSD/NVMe workspace volume
  • One non-admin local account per team member
  • NTFS ACLs: member, Administrators, and SYSTEM only
  • Cloudflare Tunnel; no public OctiqFlow ports

Development toolchain

  • Visual Studio Build Tools 2022 and MSBuild
  • .NET Framework 4.8 Developer/Targeting Pack
  • Required Windows SDK, NuGet, and ASP.NET build components
  • Git for Windows, PowerShell, Node.js, and pnpm
  • Claude Code CLI and Codex CLI

Per-user filesystem shape

D:\OctiqFlow\Users\<user>\ ├── profile\ # OctiqFlow chats, settings, agents, workspace registry ├── home\ # user-specific CLI configuration and credentials └── workspaces\ ├── project-a\ # independent Git clone └── project-b\ # independent Git clone
Do not share the full home directory. The team may use one upstream Claude/Codex account, but every Windows user should retain separate local CLI session and configuration files. This prevents local history mixing and concurrent credential-file writes.
Access model

Share URLs, not a loose HTML file or token

The OctiqFlow interface depends on its backend WebSocket, authentication endpoints, PTYs, filesystem, and Git services. Team members should receive clean hosted URLs.

Initial rollout

Use one hostname per member. It is simple, matches today's OctiqFlow authentication model, and requires no identity-aware routing layer.

Possible later upgrade

A single flow.company.com URL would require a gateway that verifies identity and routes both HTTP and WebSocket traffic to the correct runner.

GitHub and repository boundaries

Personal credentials, independent clones

Local isolation

  • Each member signs in to GitHub under their own Windows user.
  • Each account has its own Git credential store and .gitconfig.
  • Commit name/email and push identity remain personal.
  • No shared Git working directory, index, stash, or build output.

Remote safety

  • Use a personal/task branch for each piece of work.
  • Protect main and release branches.
  • Disable force-push on protected branches.
  • Merge through PR review and repository rulesets.
Capacity guidance

Size for builds, not for the web page

The browser UI is light. Parallel MSBuild, Rust, Node, test, and agent processes determine the server size. Dedicated CPU and fast storage matter more than a low-cost shared VM tier.

Migration approach

Move safely in four controlled phases

PHASE 01

Compatibility pilot

Prove OctiqFlow, PTY streaming, Claude/Codex, Git, MSBuild, and service startup on one Windows Server test user.

PHASE 02

Server foundation

Create user boundaries, install toolchains, configure NTFS ACLs, tunnel routes, monitoring, quotas, and backup.

PHASE 03

User migration

Clean-clone pushed work, transfer uncommitted files separately, migrate selected OctiqFlow profile data, and authenticate GitHub.

PHASE 04

Team rollout

Issue member URLs, verify privacy boundaries, observe real load, adjust quotas, and keep laptops available during the transition.

Transfer

  • Committed work: push, then clean-clone on the server.
  • Uncommitted work: transfer patch plus untracked files.
  • Secrets and local databases: migrate through a separate secure path.
  • Selected chats/settings: copy the user's OctiqFlow profile.

Rebuild

  • Do not copy node_modules, target, or build output.
  • Recreate dependencies and caches on the server.
  • Replace old local paths in the workspace registry.
  • Run repository build and test commands before handover.
Release gate

Validate Windows behavior before team adoption

The present repository is already a headless Rust server and browser client, but its service installation workflow is macOS-oriented. Windows operation must be proven, not assumed.

Functional checks

  • octiq-server.exe starts and serves the complete web client.
  • PowerShell PTYs accept input and stream output reliably.
  • Claude and Codex start, stream, resume, and survive browser reconnects.
  • Git status, diff, commit, pull, and push work.
  • A representative .NET Framework 4.8 solution builds and tests with MSBuild.

Isolation and operations

  • A member cannot list, read, or modify another member's directories.
  • Browser events and chat history never cross user instances.
  • Service startup loads the correct Windows user profile and environment.
  • CPU, memory, process, and disk limits are effective.
  • Snapshots restore uncommitted workspace and OctiqFlow profile data.
Known boundaries

Accepted trade-offs and remaining risks

Shared provider identityClaude/Codex usage and credentials are not isolated between trusted team members. This is an explicit accepted constraint.
Remote Git conflictsSeparate clones prevent local interference, but GitHub branch protection is still required to prevent remote overwrite.
Host administrator trustWindows administrators can access user data. Stronger protection requires separate VMs or encryption with a different trust model.
OctiqOS database scopeIf the team uses /os, do not point all instances at one existing non-tenant-aware database. Use separate databases or add tenancy first.
Single-host failureWithout snapshots and off-host backup, a server disk failure can destroy uncommitted work that is not present on GitHub.
Windows proof requiredThe Windows PTY, service-account profile, file watcher, and CLI lifecycle must pass the pilot gate before rollout.
Recommendation

Start with a private Windows development host

Windows Server 2022 + one Windows user and OctiqFlow instance per member + private repo clones + individual GitHub login + accepted shared Claude/Codex account + per-user Cloudflare Access URL.

This is the shortest path to removing laptop performance constraints while preserving the privacy boundaries the team needs. A shared single-URL control plane, Windows containers, or per-user Hyper-V VMs can be considered after the pilot provides real usage data.
